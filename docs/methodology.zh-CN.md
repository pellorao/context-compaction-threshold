# 方法与统计数据

本文记录项目的固定规则和各个 profile 的数据统计。README 保持简短，只指向这里。统计数据来自生成的 `result.json`。维护者机器上的 Claude Code 对话记录还在增长，重新运行会得到略有不同的数字。

## 数据布局

所有数据都按（harness，profile）组合存放，路径由这两个名字推出：

| 内容 | 路径 |
|---|---|
| 脱敏后的压缩样本（校准输入），已提交 | `data/<harness>/<profile>/compactions.json` |
| 分析结果（页面的唯一输入），已提交 | `data/<harness>/<profile>/result.json` |
| 图表页，部署时生成，被 git 忽略 | `artifacts/index.html`、`artifacts/<profile>.html` |
| 原始私有会话（不在仓库里；示例位置） | `.tmp/sessions/<harness>/<profile>/`，用 `--session-root` 传入 |

下面的统计数据就是这些 `result.json` 的内容。git 里只存 `data/` 下的数据；Cloudflare Pages 用 `python3 src/generate.py --render-only` 构建页面，它只读已提交的 `result.json`（会话日志是私有的）。

### 重建已发布页面

在工程目录运行 `python3 src/generate.py --render-only`。仓库里的六份结果、模型配置、双语文案和渲染代码，足以重建首页及六个模型页，不需要原始会话、重新拟合或联网。14 天筛选只在分析时执行；渲染使用保存的快照，不会随着日期变化自动淘汰其中的数据。

脱敏压缩文件保存校准输入，不包含重跑分析所需的普通请求历史。重新分析时，应使用私有的冻结会话及其清单，沿用清单记录的分析会话排除项，并指定 `--snapshot-at`。时间戳只能固定会话开始时间的筛选范围，不能冻结持续增长的日志目录。新结果用 `--output-dir` 单独保存，这次运行的压缩样本也随之存到该目录；要用已有校准文件时用 `--compactions`。原始会话、私有清单和生成的 HTML 都不提交。

## 固定规则

### 阈值网格

- 阈值是触发压缩时的上下文大小，单位是 token。
- 所有 profile 的网格步长都是 **2000 token**。已发布的 DeepSeek 曲线本来就是 2000。这是项目规则，不是各模型自己的选择，有测试检查。
- 网格必须从高于 profile 压缩后上下文的位置开始：触发点不高于它时，压缩后马上又超过阈值，每个请求都会压缩，费用轴会被拉歪。分析遇到这样的网格会拒绝运行，测试检查已发布的结果。
- 费用纵轴只覆盖曲线和浅色范围所在的区间（两端各扩到刻度，至多五个等距的整齐刻度），不从 $0 开始，这样不同触发点之间的差别看得清。跨模型比较高低时要看刻度数值。
- 网格落在步长的偶数倍上，所以悬停时读到的是 200K、300K 这样的整数。网格下限是不小于最小可设触发点的最小 2K 倍数。网格上限是不超过**最大有效触发点 = 最大设置值 - 实测缓冲**的最大 2K 倍数。有测试检查每个网格点都是 2000 的倍数。如果某个模型的这个最大值无法从权威来源核实，就不填该 profile 的横轴上限，把问题交给维护者。
- Codex 上的 DeepSeek Flash 保持已发布的横轴，64K 到 900K。Codex 没有“窗口加缓冲”这种设置，所以它的页面只显示触发点。

### Codex 订阅模型（GPT-6.1 Sol、GPT-6.1 Terra、GPT-6 Luna）

- 每个 profile 使用自己的普通请求和压缩校准数据，沿用模型前缀筛选、排除规则和响应标识去重。没有发生压缩的会话也计入普通请求工作负载。
- `session_max_age_days: 14` 按会话记录的开始时间，选择分析快照前 14 天内开始的会话。更早开始的会话即使最近继续过，也整段排除。筛选在请求去重之前进行，普通请求、压缩样本、普通请求耗时拟合和压缩后上下文测量都使用同一批会话。开始时间未知或晚于快照的会话被排除，不使用文件修改时间。
- `--snapshot-at` 接受带时区的时间戳；不传则以当前协调世界时为基准。三个已发布 profile 使用同一份冻结快照。结果的 `snapshot.session_selection` 记录包含两端的会话开始时间范围。
- 维护者确认这三个 profile 使用 **872,000 token × 95% = 828,400** 的最大有效触发点；向下取到 2K 网格后，上限是 **828K**；下限 Luna 和 Sol 是 **64K**，Terra 是 **70K**（见上面的网格下限规则）。这是约定的 Codex 边界，不是接口模型目录的上下文窗口，也不表示默认窗口是 872K。[官方配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)分别定义了 `model_context_window` 和 `model_auto_compact_token_limit`。
- 相对费用采用下表的官方接口标准输入、缓存读取和输出权重，所有上下文长度使用相同权重。按本项目约定的订阅口径，不加长上下文附加费；不估算套餐额度或购买点数的消耗。统一的费率倍数会在相对费用中消去，但随上下文变化的附加费会改变曲线。这些 Codex 记录没有单独的缓存写入；profile 中未使用的缓存写入字段取普通输入权重，不代表接口缓存写入费率。
- 三个模型各用自己的有计时压缩，摘要大小取常数均值；压缩后的上下文和未缓存输入，取压缩后第一个普通请求在拼接前的中位数。普通请求的上下文耗时斜率从这些会话拟合，不使用 DeepSeek 的受控测量。沿用 Codex 的压缩最小到最大情景、块长 8、100 次自助法重复和种子 20261031。

### Claude Code 的触发点（Opus 5.5、Sonnet 5.5）

设置项是 `autoCompactWindow`（全局，或在 `modelSettings` 下按模型设置）。

| 事实 | 取值 | 来源 |
|---|---|---|
| 允许的窗口 | 100K 到 1M token | Claude Code 设置参考中的 `modelSettings.autoCompactWindow`（“a number of tokens from 100000 to 1000000”）；模型配置页面；已安装的 Claude Code 2.1.316 内的设置说明 |
| 模型上下文窗口 | Opus 5.5 和 Sonnet 5.5：1M | claude-api skill 的 Current Models 表（1M 上下文，128K 最大输出）；Claude Code 模型配置页面（Opus 4.7 及以后、Sonnet 5 及以后默认使用 1M 窗口） |
| 窗口上限 | 有效窗口取设置值与模型窗口中较小的一个 | 模型配置页面（Claude Code 把它限制在模型自身的上下文窗口内） |
| 缓冲 | 33K | 文档：1M 窗口下“Sessions auto-compact at about 967K tokens by default”。已安装的 Claude Code：触发点 = 窗口 - min(最大输出, 20K) - 13K = 窗口 - 33K。日志：在记录这些会话时设置的 300K 窗口下，自动压缩输入的中位数是 267.9K（Opus）和 267.8K（Sonnet），即实测缓冲 32.1K（Opus）和 32.2K（Sonnet） |

由此得到：

- 最小有效触发点 = 100K - 33K = 67K，最大 = 1M - 33K = 967K。
- 网格：**68K、70K……966K**（这个范围内 2K 的偶数倍）。应当设置的窗口是 `autoCompactWindow = 触发点 + 33000`，所以是 1000 的奇数倍（101000、103000……999000），设置项接受这样的值。触发点一律显示成整数的 K（“116K”，不写“116,000 token”），因为网格落在偶数 K 上。页面和悬停提示显示所选触发点对应的窗口值，直接写成可复制的设置值（例如 `153000`），一律是整数的千：触发点 + 缓冲四舍五入到最近的 1K（五入），所以即使实测缓冲不是整数，也不会出现小数。
- 两个模型的缓冲相同，因为缓冲只通过 `min(最大输出, 20K)` 与模型有关，而两者的最大输出都是 128K。日志里没有记录每次压缩时生效的窗口，所以实测缓冲假设记录这些会话时设置的是 300K 窗口。
- 这里无法验证的一点：所有套餐是否都能为这两个模型使用 1M 窗口。文档没有限制，300K 及以下的窗口有日志佐证。

### 费用轴：每 100 万个计费 token 的费用

每个 profile 的费用轴都做了归一化，这样不论分析了多少历史数据，图都能互相比较。

- 真实历史的计费 token 数 `N` = 普通输入 + 缓存写入（5 分钟和 1 小时）+ 缓存读取 + 输出，对所有纳入且去重后的请求求和。每个 profile 一个常数，由历史数据算出，保存在 `result.json` 的 `snapshot.billed_tokens`，构成保存在 `snapshot.billing_mix`。
- 某个阈值下画出的费用 = 该阈值下重放得到的总费用 /（`N` / 1,000,000）。除数**不是**该阈值下重放的 token 数，那个数会随阈值变化，会让曲线失真。
- 因此，作为基准的这一百万 token 具有这些会话真实的计费构成。所有费用数字都按它计算：图、悬停提示、快速选择和下面的关键数字。`result.json` 同时保存总美元（`cost_usd_off_peak`）和归一化后的值（`cost_per_million_tokens`）。
- 次数用同样的方式归一化。悬停提示显示每 100 万个计费 token 的压缩次数（重放得到的压缩次数除以 `N` / 1,000,000），保留 5 位小数：所有 profile 网格上最小的值是 0.00103（Sonnet 在 966K），最大是 2.84（gpt-6.1-terra 在 70K），5 位小数能在任何地方保留至少两位有效数字。有测试检查。时间显示为模型请求时间的占比（见下文“时间占比”），不随历史多少而变。页面上的其他数字要么是比例、价格、拟合系数，要么是对数据的描述（会话数、请求数、小时数）。
- 压缩请求本身不计入 `N`（Claude Code 的对话记录里没有它们，Codex 里的压缩请求会被去掉，见下文），但计入重放费用。
- DeepSeek Flash 用同样的方式归一化。它最初发布的曲线是较小历史的总美元，没有 token 总数，所以用 Codex 会话重新计算过。
- 显示单位：页面把费用显示为相对坐标轴最大阈值处中心费用的变化（`cost / cost_max - 1`，百分数，最大触发点处为 0%）。页面不显示美元；每 100 万 token 的绝对美元数只保留在 `result.json` 和本文档里。浅色带相对同一个中心基准，而不是相对它自己所属情景在最大触发点的值。

### 哪些会话和请求会被计入

Codex（`~/.codex/sessions`）：

- 提供方等于 profile 的提供方，或模型名以某个 profile 前缀开头的会话。
- 请求按 response ID 去重。
- 工作目录包含 `smoke`、`probe` 或 `test` 的会话被排除，用于测量压缩耗时的会话也被排除（`--exclude-thread`）。`--active-thread` 排除分析会话本身，并加入它最后一次压缩之后的最新一段。
- Codex 把每次真实压缩记成一个压缩请求，紧接着是一条 `compacted` 记录。这个请求会从会话里去掉（它不计入 `N`，压缩由重放自己建模），压缩前后的两段则像 Claude Code 那样（见下文）接成一条未压缩的请求流。没有这一步时，真实压缩处上下文骤降，会让重放的上下文变成负数，所有费用都变成负的。
- 提供方等于 profile 的提供方，或模型匹配的会话是候选；但只有它用到的每个模型都以某个 profile 前缀开头，才会被纳入。两个使用 `deepseek-v4-pro` 的会话（62 个请求）只因提供方相同而被匹配到，已按 `other-model` 排除：这个模型的价格不同。
- 每个请求都有时长（见下文“时间占比”和“从日志计时”）。分析会话和其他纳入会话里的真实压缩会变成压缩样本；用于手工计时的会话不取样本，这样没有压缩被重复计算。

Claude Code（`~/.claude/projects/**/*.jsonl`）：

- 只取模型名以 profile 前缀开头的 `assistant` 记录：`claude-opus-5-5`、`claude-sonnet-5-5`。其他版本，例如 `claude-opus-4-8`，因为价格不同而被排除。
- 请求按 `message.id` 全局去重。一个回复被拆成多行流式写入时只算一次，取最大的 `output_tokens`。消息 ID 会在不同文件间重复（分叉和恢复会话），所以去重跨所有文件。
- 子代理的对话记录也计入。它们用同样的机制压缩，并且占了大多数压缩（Opus 的 261 次中有 168 次）。
- 一个对话记录文件就是一个会话。没有匹配请求的文件被排除。
- 缓存写入 token 按每个会话真实的 5 分钟、1 小时写入构成计价，由此得到该会话的“未缓存 token 价格倍数”。
- 每个请求都有时长（见下文“时间占比”和“从日志计时”），主对话和子代理一视同仁。

### 时间占比

橙色线是**压缩占模型请求时间的比例**（下方时间图中的橙线，与模型总耗时线共用一根纵轴：下端略低于总耗时变化的最小值，上端固定为 20%，超出部分裁掉）。对每个代理（主对话或子代理）一视同仁：它自己的压缩请求秒数，除以它自己全部模型请求（含压缩请求）的总秒数。它与被调用的代理、空闲间隔、工具执行时间、会话持续多久都无关。跨会话时按合并比例计算：压缩秒数之和除以请求秒数之和，不是各会话占比的平均。

- 每个请求保留它在真实会话中的时长（`Request.seconds`）。分块自助法把每个请求的变化连同它的时长一起重采样，所以每次重复有自己的请求总时间。
- 重放里的每次压缩，把它建模的秒数同时加进分子和分母。真实压缩从请求流中去掉（它们不是重放的请求），所以分母只含普通请求加上建模的压缩。
- 普通请求保留观察到的时长，并按重放的上下文调整（见下一节），所以请求秒数 `R_T` 随阈值变化。
- `时间占比 = 压缩秒数 / (R_T + 压缩秒数)`。`result.json` 在每个曲线行里同时保存两个和（`compaction_seconds`、`request_seconds`），并在 `snapshot.request_seconds` 保存真实历史的请求秒数。页面用滑块调整后的压缩秒数，除以同一个重复平均的 `R_T`。
- 与真实历史对照：在真实自动压缩所用的触发点上，重放占比与观察占比一致。Opus：261 次真实压缩用了 15,431 秒，总共 424,853 秒的请求加压缩时间（3.63%），266K 触发点的精确重放给出 3.56%。Sonnet：观察 2.64%，266K 精确重放 2.25%（只有 24 次压缩，噪声较大）。DeepSeek 的观察值 4.82% 不可比（重放在 266K 给出 5.5%），因为 25 次有计时的压缩包含分析会话的压缩，而重放只把分析会话当作尾段接上。
- 空闲间隔规则（超过 300 秒的间隔）和工作时间概念，连同“代理时间对墙上时钟”的区分一起移除：分析中不再有任何地方依赖它们。

### 请求耗时、模型总耗时和相对单位

普通请求带的上下文越多，耗时越长。重放对此建模，同时算出模型总耗时作为第二个指标。它在每个页面上都画成时间图的紫线（见“结果”一条）。

- 拟合：每个 profile 对所有纳入的请求（压缩请求不在流里；时长未知、用中位数补上的请求也算进去，Opus 45,356 个里有 82 个），用最小二乘把观察到的请求时长回归到请求真实带的上下文（`Request.observed`，即被拼接和重采样挪动之前的上下文）和它的输出 token 数，带截距。上下文系数 `s`（每个上下文 token 的秒数）保存为 `fitted_model.request_seconds_per_context_token`，截距、输出系数和 R2 放在旁边。
- 区间：同一个拟合在每次分块自助法重复上再做一遍（种子、块长和重复次数与曲线相同），区间取这些斜率的 10% 到 90% 分位（`..._low`、`..._high`）。斜率测得不准（Sonnet 的下端约为零），所以给的是区间而不是点。DeepSeek 是例外：它的斜率不从日志拟合，而是写在 profile 里（`config/models.json` 的 `request_slope`：中心、低、高），来自受控测量（见下）。它在重放中以及 `fitted_model.request_seconds_per_context_token*` 里取代拟合斜率及其自助法分位；`result.json` 的 `request_slope_source` 写明是 `controlled` 还是 `log-fit`，日志拟合的斜率留在 `request_seconds_per_context_token_log_fit` 供参考。
- 重放：请求在重放里的上下文是 `x_T`，观察到的是 `x_obs`，它的时长是 `观察秒数 + s * (x_T - x_obs)`。对整个工作负载求和就是 `request_base_seconds + s * context_shift_tokens`，两者都存在每个曲线行里，所以任何斜率下的 `R_T` 都可线性得出。行里保存 `request_seconds`（中心斜率）以及 `request_seconds_slope_lo`、`request_seconds_slope_hi`。低触发点上单个重放请求可能算出负值；指标用的是总和，所以不设下限（设下限也会破坏线性）。在超过观察到的最大上下文（Opus 287K，Sonnet 268K）的地方，同一个斜率是外推的。
- 模型总耗时：`W_T = R_T + 压缩秒数`（压缩秒数是按速度滑块缩放的输出部分，加上预填充部分）。不含工具执行时间和用户时间：它们不随触发点变化。它保留在分析输出和下面的表里，页面把它画成时间图的紫线。
- 相对单位：图上显示 `cost_T / cost_max - 1`（百分数；上方图的纵轴只覆盖费用线和它的浅色带；`W_T / W_max - 1` 在 Claude 页面画成下方时间图的紫线，基准和滑块速度相同，浅色带取斜率区间与压缩低、中心、高三组行的最小到最大，DeepSeek 页面同样画），基准是最大阈值（Claude 966K，DeepSeek 900K）处的中心曲线，且在同一滑块速度下。
- 浅色带：费用用低、高两个费用情景。模型总耗时和时间占比取三种压缩情景（低、中、高行）与三种斜率（低、中、高）的所有组合，取最小和最大；除以中心基准 `W_max`，所以最大触发点处的带不是零宽。
- 结果见下面的表。页面把它画成时间图里的紫线，并显示在卡片和悬浮提示里，按滑块速度实时重算。按实测速度：触发点从 150K 往下降时，模型总耗时快速增长（100K 处 Opus 约 +10%，Sonnet 约 +17%，浅色带整体在 0 以上），200K 以上与最大触发点相差在约 ±2.5% 以内。DeepSeek 页面也画，斜率来自一次受控测量：通过 Codex 对 `deepseek-flash`（高推理强度）发出 384 个请求（分两个夜间时段跑 4 个区块，每块 2 轮、8 个上下文规模，从 16K 到 900K，每个规模 1 次冷启动加 5 次命中缓存；共 320 个命中缓存、64 个冷启动）。命中缓存的请求（正常情况，缓存命中约 99.9%）给出每 100K token 0.96 秒（普通最小二乘，截距 1.90 秒，R2 0.185；自助法 10% 到 90% 分位 0.75 到 1.18；各区块的普通最小二乘分别是 0.96、1.55、0.47、0.86）；稳健的 Theil-Sen 斜率是 0.31；冷启动请求给出 2.38（1.96 到 2.82）。慢请求（耗时至少是同规模中位数的 2 倍，320 个里有 48 个）按上下文规模聚集（置换检验 p < 0.001），按轮次或时间聚集弱得多（p = 0.05）：长上下文更常变慢，所以中心取均值（普通最小二乘），低值取典型请求（Theil-Sen），高值取普通最小二乘的 90% 分位。profile 取中心 0.96、低 0.31、高 1.18。所有测量都在当地夜间进行，没有覆盖白天高峰。会话日志拟合的斜率（1.30 秒，截距 -0.83 秒，小上下文处拟合差）把冷启动和命中缓存的请求混在一起，所以不用。结果对这个斜率很敏感。这三个数字只写在 `request_slope` 里。细节：Opus：相对 9.0 秒的平均请求，斜率很小，从 200K 起模型总耗时与最大触发点相差在几个百分点以内（最低点在 364K 附近）。Sonnet：300K 以上模型总耗时几乎持平。DeepSeek：相对 4.5 秒的平均请求，斜率很大，大触发点让每个请求都变慢；中心的模型耗时曲线最低点在 136K（-33.8%）。

已知局限：

- 时间戳是 harness 写下记录的时间，精度为毫秒；时长包含记录与请求发出或到达之间的任何客户端间隔。
- Codex 的压缩从上一个 `token_count` 或当前回合的 `task_started` 中较晚者起算。它不包含回合开始前的用户等待，但仍可能包含压缩请求发出前的少量客户端时间。对于手工和日志都计过时的 9 次压缩，手工计时长 0.2 到 2.7 秒（平均约 1.5 秒），这是手工方法的客户端偏移。手工行按测得值保留。
- Codex 的输入和缓存部分来自压缩请求自己的用量，不是它前一个请求的用量（同一次压缩两者最多相差约 20K token，而自己的用量才是模型实际处理的）。手工计时的行用的是同样的字段。
- Claude Code：如果回复与工具执行交错，它最后一行流式记录可能晚于回复真正的结束，使这个请求变长。摘要大小是估计值（Sonnet 的估计器只基于 33 条普通回答）。
- 两个 harness 的请求秒数都包含模型的思考时间和网络重试。

### 如何找到压缩并校准

- Codex：`data/codex/deepseek-flash/compactions.json` 保存 9 个手工计时的样本（来源为 `native` 或 `session-derived`，按测得值保留）和从日志读取的压缩（来源为 `log-auto`，只有数字）。每次分析运行会替换 `log-auto` 行，保留手工行。真实压缩同样从请求流中去掉，前后的段接续起来。
- Claude Code：样本每次分析都会写到 `data/claude-code/<profile>/compactions.json`（来源为 `transcript-auto` 或 `transcript-manual`；只有数字，没有 ID、时间戳、路径或文本），拟合再读回。子类型为 `compact_boundary` 的 `system` 记录，带有 `compactMetadata`（触发方式、`preTokens`、`durationMs`）。摘要是紧随其后、标记为 `isCompactSummary` 的用户记录。边界按时间戳和 `preTokens` 去重。如果压缩前没有请求、没有耗时或大小、或没有摘要文本，这次压缩就不用于校准。
- 压缩请求本身不在对话记录里。它的输入是压缩前的整个上下文：除了一小段未缓存的尾部（`preTokens` 减去最后一次请求的上下文），全部是缓存读取；尾部按该会话的倍数作为缓存写入计价。
- 摘要 token 数由摘要文本估计。普通回答（只有文本，扣除思考 token）的输出 token 数，对汉字个数和其他字符个数做回归（普通回答里没有汉字时，所有字符共用一个比率）。
- 压缩耗时 `t_c = a * C + G / v` 在各次压缩上无截距拟合（Claude Code 上 `C` 是整个压缩输入，Codex 上是其未缓存部分，`G` 是摘要 token 数）。Claude Code 上摘要 token 数服从 `G = g0 + g1 * C`。Codex 上 `G` 是常数，取有计时的摘要的均值（harness 设置 `summary_grows_with_input`）：25 个样本里 `G` 与 `C` 的相关系数是 0.17，拟合斜率（每个 token 0.0020 token，标准误 0.0024）与零无差别，留一法检验也支持常数（RMSE 1,611 token，线性拟合是 1,753；对数线性拟合 1,619，没有更好）。之前的线性模型（9 个手工计时样本）在大上下文上高估了 `G`：它把 888K 那次压缩的摘要估成 9.9K token，实测是 4.5K。
- 压缩后的上下文及其未缓存部分，取每次压缩后第一个请求的中位数（Claude Code），或取实测值（DeepSeek）。
- 真实的自动压缩都发生在同一个水平（Claude Code 约 267K，Codex 约 300K），所以更高的触发点从未被观察到。每个会话被真实压缩切开的各段，会接成一条未压缩的请求流：后一段从前一段的上下文出发，加一个中位数增量，未缓存部分取中位数。因此约 267K 以上的曲线是外推得到的。
- 如果某个模型自己的压缩少于 50 次（harness 设置 `min_fit_compactions`），并且 profile 指定了 `borrow_calibration` 的来源 profile，拟合就同时用自己的压缩和来源模型的压缩，来源模型的样本从它的 `compactions.json` 读取（借来的行是拟合时的规则，不会复制进该模型自己的文件）。来源模型的耗时要乘以一个倍数：对该模型自己的每次压缩，用实测秒数除以来源模型拟合结果对这次压缩的预测秒数，再取这些比值的**中位数**。用中位数是为了让某一次特别慢的压缩几乎不影响倍数。页面和下面的统计表都会标明这一点。没有来源模型时运行会停止。

### 重采样

- 对每个会话真实的逐请求变化做循环分块自助法：块长 **8 个请求**，**100 次重复**，种子 **20261031**。
